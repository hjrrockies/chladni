# Session note, 2026-09-19: the CI disagreement, and four mechanisms it is not

*Working notes, addressed to a moment. This records what was measured while investigating
`TODO.md` section 1's blocking item, in the order it was measured, because the order is the
result: the stated cause was refuted three times before the real shape of the thing appeared.*

## What the blocking item said, and what is left of it

On 2026-09-18 `TODO.md` and `docs/design/search.md` recorded a **platform-dependent silent wrong
total**: on `ubuntu-latest`/`scipy-openblas32`, `test_the_cluster_total_GRID[N65-1e-06-b2.6]`
declares 3 of 4 where macOS/Accelerate declares 4, and the cause was given as *"a different
LAPACK moves the GSVD at the 1e-15 level, and this grid is built to sit exactly at that edge."*

**The failure is real and the stated cause is wrong.** What survives measurement is narrower and
stranger: the wrong total needs the OpenBLAS arithmetic **and** the whole test suite's worth of
preceding state, and neither alone produces it.

## The cell is not at a 1e-15 edge, which is where the stated cause fails

At `prec = 1e-6`, band 2.6, `N = 65`, the four members sit **2.60 / 5.72 / 2.60 licences** apart.
A 241-point scan finds four separate wells, minima about 3.0e-07, and the barriers between them
at **1.258e-05 / 2.773e-05 / 1.234e-05** -- four orders above the wells. Nothing about this cell
is tight, so "built to sit exactly at that edge" does not describe it. The tight cells on this
grid are at `prec = 1e-14`, and `basis_sufficiency` already excuses those.

## Three mechanisms, measured and refused

Each was the obvious candidate, and each is negative. Recorded in full so the next reader does
not spend the day re-running them.

| proposed mechanism | how it was tested | result |
|---|---|---|
| the GSVD backend | `gsvd4py` pinned onto `scipy_openblas32` ON macOS -- Accelerate wins its strategy-1 probe, so the library was loaded the way strategy 3 would | `sigma_1` at truth moves 2% inside the 1e-15 floor; same four minima, same barriers, **total still 4** |
| rounding in the objective | the tension vector jittered multiplicatively, 8 seeds per magnitude | **4 every run** from 1e-15 through 1e-04; DECLINES every run from 1e-02 through 0.5. Across eleven orders it is right or it declines, never silently wrong |
| the threshold rank | `rtol` nudged so the same per-`lam` rule retains 83 through 125 | 4 through rank 85, then DECLINES. **Never 3** |
| the shared pencil's cache | `prefill` of 0 to 200 extra parameters on the memoized pencil before solving | bit-identical `lam`s at every prefill; cache residency is inert, as `_CACHE_MAX`'s comment claims |

The rank deserves a note even though it is negative, because it is the one quantity here with
O(1) leverage: the cut sits INSIDE the rounding floor. At five parameters across the cluster,
`s[83]/s[0] ~ 3.3e-15` against `rtol = 1.490e-15` (2.2x above) and `s[84]/s[0] ~ 1.2e-15` (only
**1.12x to 1.28x below**). Those singular values are noise. But `gesdd`, `gesvd` and a
row-permuted matrix all return rank 85, and so does Linux -- see below -- so the margin is thin
without being crossed.

## A second platform difference, not previously recorded

**The two platforms score different case sets.** macOS calls 10 cells unexercisable where Linux
calls 7, so three cells differ. Two of the four macOS skips in `test_cluster_totals` sit on the

This matters to the central claim directly: any "N right, M wrong" compared across platforms is

a boundary it clears by 6%.

## A performance result, incidental but large

On the same `ubuntu-latest` image, same module scope:

    OPENBLAS_NUM_THREADS=1     221 s, and 284 s in a second identically configured job
    default (2 cores)          712 s

**Letting OpenBLAS use both cores is 2.5x to 3.2x SLOWER than pinning it to one.** The suite does
thousands of factorizations of a 190-column pencil, and at that size the per-call thread spawn and
synchronization cost dominates the arithmetic it parallelizes. The 221/284 spread is
runner-to-runner variance between identical jobs, so treat the range rather than either number.
If it holds at full-suite scope it would take CI's legs from ~65 minutes toward ~20. NOT measured
at full-suite scope, and not a claim about Accelerate versus OpenBLAS -- the macOS 12m38s above is
a laptop against a 2-core runner and says nothing about the libraries.

## What to do next: COLLECTION, not execution

There is an apparent contradiction in the table above, and resolving it is the next experiment.

Under alphabetical collection `test_cluster_totals.py` runs at 21% of the suite, so at the moment
the cell is scored, the only test files that have EXECUTED are the nine that precede it
alphabetically -- and that exact scope was measured on Linux, where the cell passed. Every other
file in the full suite runs AFTER the cell. So nothing that runs later can have changed what the
cell saw.

Unless it is not execution. **Pytest imports every collected module before running any test.**
Module-level code in files that execute later has therefore already run when the cell is scored:
module-level constants, case construction, `pencil_for` calls that populate `rect_suite._PENCILS`,
RNG draws, and any `warnings` filter installed at import. That is the one channel by which the
rest of the suite reaches backwards, and it is exactly what the nine-file scope does not
reproduce, because those later modules are never imported there.

The discriminator is cheap and decisive, about five minutes on a runner:

    .venv/bin/python -m pytest tests -m '' -W error::UserWarning -k "cluster_totals"

That COLLECTS the whole suite -- every module imported, every import-time side effect present --
and EXECUTES only this module's tests. If the cell declares 3 of 4 there, the trigger is
import-time state and the hunt narrows to module-level code in the later files. If it declares 4,
the trigger needs the earlier tests to actually run, and the nine-file result says they are not
sufficient, which would leave accumulated process state as the remaining candidate.

Whichever it is, the mechanism must also explain state B -- why Linux at module scope stops
declining in `cross_check_LOSES...[2.0]` where both macOS and Linux-at-full-suite decline.

Do not re-run: the backend swap, the jitter sweep, the `rtol` rank sweep, the cache prefill, the
threading comparison, or any narrow-scope Linux probe of this cell. All negative, all recorded
above.

## Why the refiner refuses it

> **WRONG -- superseded by the 09-21 trace below.** Everything in this section is inference
> from the code, and the trace refutes it: the refusal is `not_a_minimum` at a rank-flipped
> bracket end, not `no_parabola`. Kept because the reasoning shows how a plausible story

    ends = (hist[0][2], hist[2][2])

Every other ending is judged on two conditions, and both pass comfortably here: the located

endpoint values of about 1e-05 on the well's flanks. So `_accept` would have taken this root.

And the fit has nothing to close on. **This well bottoms out AT the arithmetic floor**:
`sigma_1` at the true eigenvalue is 2.03e-15 against a rank cutoff `rtol` of 1.49e-15, the same
order. Near the minimum the objective is not a parabola, it is rounding noise -- so a threaded
BLAS that perturbs the last bits perturbs exactly the quantity that decides whether the fit
closes, which is why one thread never fails and two sometimes do. The six extra refinement
evaluations are the shape of a refiner that kept stepping because nothing settled.

`notes/session_2026-09-17.md` records that a `no_parabola` START was already a known rough spot
-- "the last wrong cell ... was 2 of 3 until the refiner stopped giving up on a start with no
parabola". An ENDING in `no_parabola` is still an unconditional refusal.

not the reason, which was a gap in it. `SolveDiagnostics.rejected_deep` now carries
`(lam, sigma, reason)`, so the next Linux run states it instead of leaving it to inference.

## The rule, and what it costs

> **One claim here is WRONG -- see the 09-21 trace.** "wrong cells flagged 1 of 1" was
> measured on macOS, where the N65 cell is RIGHT; the one wrong cell in that table was an
> over-count at `145*pi^2`. On Linux the rule does not flag the N65 cell at all.

`search._deep_rejections`: **a rejection is suspicious when the `sigma_1` the refiner reached is
no larger than the WORST accepted level's**, and those reach `n_uncertain`, so
`certified_counts` is False and `solve_interval` raises.

It needs no new constant, which is the point -- the accepted levels supply the scale, so it
travels to a domain whose floor sits elsewhere. An empty bracket is refused on the barrier
between wells; on this cell that barrier is 1.2e-05 against located roots at 2.6e-11 to 4.1e-07.

Measured on macOS over all five grids, 251 exercisable cells:

    cells with ANY rejection            35
    of those, flagged as deep            2
    FALSE ALARMS (right but flagged)     1     at prec 1e-14, sigma 2.57e-15, not_a_minimum
    wrong cells flagged                  1 of 1

Selective: quiet on 33 of 35 rejections. The comparison that matters is the blanket rule
withdrawn in `session_2026-09-17.md` -- flag every rejection that is not
`not_a_minimum`/`endpoint` -- which scored 24 false alarms and 0 true positives. The difference
is that this one keys on DEPTH rather than on the reason string.

The single false alarm is at `prec = 1e-14`, where every `sigma` in the problem sits at the
floor and "as deep as an accepted level" stops discriminating. That is the regime
`basis_sufficiency` already excuses for a different reason, and it is the honest limit of the
rule.

# 2026-09-21: the trace, and a mechanism that is OBSERVED

The loudness rule merged 2026-09-20 did not fire on the first Linux CI run after it -- the cell
still read `declared 3 of 4; n_uncertain=0`. So the refiner was traced on a Linux runner DURING
the cell's real solve, in the nine-file scope at default threading, recording every refinement
with every evaluation and the retained rank at each (`len(tensions)`). Throwaway branch
`diag/refine-trace`. It reproduced 3 of 3, and the three traces are **bit-identical**.

The other three brackets are accepted, `converged`, in 2 to 3 evaluations each. **That upper end
is the only rank-86 evaluation in the whole refinement stage**, and rank 86 never appears on

So: one flip, at one end, lowered `sigma_1` there enough to make the end the deepest point the
refiner held (5.18e-7 against the hint's 5.51e-7). It stepped toward that end, never came within
3.5e-5 of the root, found the best point AT an end, and `_accept` refused it. `not_a_minimum`, not
`no_parabola` -- the 09-20 inference was wrong.

## Why only on Linux, and why the rate moved with scope

At Linux's exact upper end, macOS retains rank 85 with `s[85]/s[0] = 1.329e-15`, **0.892x the
cutoff**. OpenBLAS's value came out at least 12% larger. For a singular value at 1.3e-15
relative -- rounding noise -- that is an ordinary cross-BLAS difference.

The flip's EFFECT reproduces across platforms; only the DECISION differs. macOS's rank-86 pencil
at the same point gives `sigma_1 = 5.33e-07` against Linux's 5.18e-07. But that effect is jagged
in `lam`, because direction 86 is noise:

    offset from Linux's upper end    rank-86 / rank-85
    -4e-06                           0.962
    -2e-06                           0.781
    -1e-06                           0.461
     0                               0.328
    +1e-06                           1.000

A 67% drop to none across **8e-9 relative**. At macOS's own bracket end the same flip lowers
`sigma_1` only 3%, not enough to matter. So the failure needed two coincidences: the rank decision
landing on 86, AND the bracket end landing on a spike of that jagged function. Stage 1's slope
estimate differs across platforms in the fifth digit, which moves the bracket end -- and that is
why the RATE moved with scope while no scope determined the outcome.

## Why `_deep_rejections` stays silent

The refused point is the flipped END, a flank point at `sigma = 5.18e-07`. The worst located level
is `4.08e-07`. Shallower, so the rule reads `()`. A depth test cannot distinguish "an end made
artificially deep" from "an empty bracket", and neither can anything that reads only the values
the refiner already has -- the defect is that those values are discontinuous.

## Exposure is general, not this cell's

For every evaluation of this cell's solve on macOS, where the rank decision sits:

    [0.95, 1.00)                               0
    [0.90, 0.95)                               2

## What this settles, and what it leaves

Settled: the Linux wrong total is a discontinuity in the objective introduced by the threshold
rank, meeting a refiner that trusts its endpoints. Everything that looked like platform or scope
dependence is those two coincidences.

Left: the remedy -- a regularization with no discontinuous rank jumps, in progress -- and its
acceptance test above. Not recommended as a stopgap: sharpening `_deep_rejections` (it cannot see
this), or a refiner heuristic that distrusts ends (it would be treating the symptom of an objective
that should not jump in the first place).
